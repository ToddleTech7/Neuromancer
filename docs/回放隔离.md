# 回放隔离：只读、沙箱与生产环境的边界

> 适用范围：所有“把输入事件重新投递到浏览器”的回放功能，以及以后新增的写操作回放。
> 这条不是性能优化，是**安全边界**：回放不能改变生产 CAVE 的 operation、root 或版本。

## 结论

历史复现和写行为验证要分开：

| 模式 | 数据 | 凭据 | 写请求 | 目的 |
|---|---|---|---|---|
| 历史复现 | 固定版本 / 只读快照 | 只读 token 或无凭据 | 禁止 | 看当时画面、验证输入回放 |
| 写行为沙箱 | 生产图副本 / 可重置 sandbox | 独立 sandbox 账号 | 只允许 sandbox | 测试 merge / split / undo |

**默认永远是历史复现；写行为验证只进沙箱，不进生产。**

## 为什么只读数据源还不够

只读数据源只能保证“读的是旧版本”，不能保证“写入不会发到生产”：

- 回放的是原始 pointer / wheel / key，点到「Merge」「Split」「Undo」会再次发写请求；
- 页面可能仍带生产 Cookie、token 或浏览器会话；
- 客户端 guard 可能被绕过，或者某些回放路径根本没有注入 guard；
- 单靠“数据源只读”无法阻止后端产生新的 operation / root / 版本。

所以需要多层隔离。

## 隔离层

### 1. 浏览器与凭据

- 使用独立的浏览器 profile，不复用生产登录态；
- 只读回放使用只读 token，或完全不使用 CAVE 写权限；
- 不把生产 token 写进会话包、截图、日志或回放脚本；
- 沙箱回放使用独立账号，只对 sandbox 有权限。

### 2. 客户端只读 guard

在回放页 document-start 注入：

- 拦截所有非 `GET` / `HEAD` / `OPTIONS` 的 `/api/` 请求；
- 拒绝请求并记录 `blocked_attempts`；
- 回放报告里显示 guard 是否启用、拦截了什么。

现有实现：`cave_replay_viewer.py` 的 `GUARD_JS`。
`replay_manual_session.py` / `verify_action_replay.py` 目前只对本地 demo server 回放，所以没有注入；
以后若增加“真实 CAVE 地址”入口，必须同时注入 guard。

### 3. 网络与后端

客户端 guard 不是服务端权限：

- 回放网络只允许读取数据端点，禁止生产写端点；
- 服务端对回放凭据拒绝写，不能只靠前端；
- 沙箱使用独立后端，演练结束可重置；
- 审计日志记录零生产写调用。

### 4. 数据版本

- 使用固定版本 / 历史快照，不用当前 live segmentation；
- 记录 `at` / `version` / `snapshot` 指针；
- 资产过期、撤权、缺失要返回明确状态，不静默换成最新版本；
- 回放结果标明 `visual_replay_status`，不把“看起来像”写成“版本一致”。

## 当前项目状态

已安全的路径：

- `replay_manual_session.py`：本地 `cave_local_demo_server`，无 CAVE 写端点；
- `verify_action_replay.py`：本地 demo，无 CAVE 写端点；
- `cave_replay_studio.py`：本地 demo iframe；
- `cave_replay_viewer.py`：本地 demo + `GUARD_JS`；
- `cave_session_replay.py`：静态 HTML，不连生产。

记录但不会重放的写信息：

- `edit.request`、`api.request`、`edit.ack`、`edit.operation` 只用于观察和 join；
- `inputs_of()` 只取 pointer / wheel / key，不发送记录下来的写请求。

仍需注意：

- 输入回放会重放**点击**；在真实可写页面上，点击可能重新触发写操作；
- 当前 `replay_manual_session` / `verify_action_replay` 没有客户端 guard；
- 只读 guard 是浏览器侧保险，不是服务端权限；
- 不要把回放改指向生产可写 CAVE 作为“快捷验证”。

## 新增回放/写功能前的检查

- [ ] 目标是本地、历史只读，还是 sandbox？生产可写是否明确禁止？
- [ ] 凭据是否只读？是否与生产账号隔离？
- [ ] 是否注入客户端 guard？是否记录 `blocked_attempts`？
- [ ] 服务端/网络是否也拒绝写？是否有审计？
- [ ] 数据是否钉在版本/快照上？过期/撤权是否明确报错？
- [ ] 沙箱是否可以重置？回放产生的 operation 是否留在沙箱？
- [ ] 报告是否区分“只读复现”和“写行为沙箱”？

任何一项答不上来，就不应该把该回放功能接到真实生产环境。
