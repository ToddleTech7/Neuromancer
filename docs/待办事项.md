## 这份文件收什么

只收**不依赖任何产品决策就能开工**的项：卡在"要改 Neuroglancer 源码"或"要私有 CAVE 加接口"。
不依赖你拍板的规则/形态问题另见 `当前进度` 与对话结论；插件的当前能力边界仍是 `当前进度`，本文件只写**做不到的那部分怎么补**。

维护约束：

1. 每项写清 **依据哪个 ID → 现在怎么近似 → 为什么插件真做不到 → 改哪里 → 怎么算改完**。缺一项就不算可交接。
2. 改完必须同时更新三处：`cave_recorder.user.js` 的 `capabilities()`、`当前进度`、`开发记录.md`。
3. 在做到之前，这些字段一律视为**不存在**，不用"没有值"反推"没有发生"。

## 必须改 Neuroglancer 源码的项

### F-01　规范化动作 ID（RF04，P0）

| | |
|---|---|
| 依据 | RF04 要求"规范化 action id"；PP04 要求把工具语义在线落成事件 |
| 现在怎么近似 | `input.key` 只给 `key_combo` + `action_source: 'unmapped'`；读不到 action dispatcher，不敢猜 |
| 为什么做不到 | 键位绑定表与 action 派发在 ng 内部（`input_event_bindings` / action dispatcher），插件只能看到裸键盘事件 |
| 改哪里 | 在 action 派发处挂一个 emit：`action_start/action_end {action_id, args}` |
| 怎么算改完 | 同一次 Merge 操作：前端 `action_id` 与服务端 `operation_id` 能对上（配合 B-01） |
| 卡点前置 | 需要 D01 里那个 fork 的 commit 与 action 清单 |

### F-02　工具态 / 模式 / 草稿 / 预览结果（RF07，P0；含 PP04）

| | |
|---|---|
| 依据 | RF07：工具/模式/草稿/preview；PP05：候选弹窗**不得打断**工具拖拽 |
| 现在怎么近似 | 防御式探测 `layer.multicut`（`partial`）；`tool_context` 从 `document.activeElement` 猜 |
| 为什么做不到 | 工具 handler 与草稿状态在 ng 的编辑工具类里，插件没有句柄 |
| 改哪里 | 编辑工具（multicut / merge / split）的 handler：`tool_select` / `draft_update` / `preview_result` |
| 怎么算改完 | 一次 Split：`draft_update` 的 sources/sinks 与 `preview_result` 的分裂形状，与服务端最终执行一致 |
| 额外好处 | 有了它，弹窗才知道"现在是不是正在拖"——这是 PP05 硬要求的 |

### F-03　V_loaded（真实加载态，RF10，P0/P1）

| | |
|---|---|
| 依据 | RF10：chunk/LOD 真的加载了什么；RB07 要 chunk manifest 的版本化引用 |
| 现在怎么近似 | **完全没有**。`viewer.state-change` 只说明"视角变了"，不说明"画面真的画出来了" |
| 为什么做不到 | chunk manager 在 ng 内部，插件看不到请求了哪些 chunk、哪些失败、哪些还在 pending |
| 改哪里 | `chunk_manager` 的加载回调 + 失败回调：`chunk_loaded {chunk_id, mip, source_version, ms, ok}` |
| 怎么算改完 | 断网跑一次：失败 chunk 必须出现在事件里；恢复网络后能看出补拉 |
| 为什么重要 | **没有 V_loaded，R2 无法证明"回放出来的画面就是当时看到的画面"**（可能当时图还没加载完） |

### F-04　真 panel_id（RF01 增强，P1）

现在只有 `canvas_index + 尺寸`。2D/3D 多面板时无法区分"哪个面板的操作"。
改：panel / viewport 结构处 emit `panel_id`。改完验收：双面板操作，事件按面板分组正确。

### F-05　3D 视锥与裁剪（RF09 增强，P2）

`partial` 只覆盖 2D 视口 + nm/px。3D 的相机位姿/裁剪面未采。
改：3D panel 的相机状态处 emit。验收：3D 视图 checkpoint 能完整复现。

### F-06　工具作用位置（RF12 增强，P2）

点击位置有，工具作用点（工具把哪个体素当成 source/sink）没有。
改：工具 handler 的落点处 emit。验收：与 B05 的服务端权威 source/sink 对比可解释。

## 必须后端（按"没有它就不能验收"排序）

### 第一组：提交回执（不做，join 只能靠时间猜）

| ID | 后端要做什么 | 字段 | 现在的替代 | 怎么算改完 |
|---|---|---|---|---|
| B-01（B01/B02 + RB01 + BV08） | 每次提交请求的尝试链、幂等重试与最终状态，可按 `client_request_id` 反查 `operation_id` | `client_request_id, operation_id, operation_type, request_outcome, attempt_n, server_time` | 本地生成 `client_request_id` 写进请求体；join 用 `exact-anchor` 或窗口，provenance 记 `simulated` | 前端超时→重试 后，服务端只有一次执行，且能按 request_id 查到最终 `operation_id` |
| B-02（B03/B04/B05） | 服务端操作顺序与时间、修改前后 root 映射、权威 source/sink 坐标 | `server_sequence, operation_timestamp, before_root_ids[], after_root_ids[], source_coords, sink_coords` | 用 op log 的 timestamp 与 operation_id 近似 | 同 root 连续两次编辑：顺序可重建，before/after 链闭合 |
| B-03（B06/B07） | 区分前端取消 / 服务端失败 / 已提交 undo；错误类型与标签来源分离 | `attempt_id?, undo_of_operation_id?, fail_reason, error_type, label_source` | 前端只能记"我没提交成功"，服务端侧空白 | 四个状态各造一例，全部可区分（前端取消不能记成服务端失败） |

**这一步的连锁影响**：没有 B-01，`cave_join.py` 的三级匹配永远停在"时间+Root 兜底"，样本里的 `process.session_id` 只能算 `simulated`。

### 第二组：版本与历史（不做，R2 只能证"画面像"，不能证"是当时那个版本"）

| ID | 后端要做什么 | 为什么绕不过 | 现在的替代与谎言风险 |
|---|---|---|---|
| B-04（B08/B09 + RB04 + BV06） | 编辑前后可重建的图状态引用 + 读时版本锁定 + 数据源/分辨率 | R2 明写"不允许串版本"；并发改动后必须按录制时间读 | 现在用"当前 seg 源"，回放一律标 `partial`；**绝不写 complete** |
| B-05（RB03/BV09） | 历史回放的**只读**数据源（sandbox/replay mode），服务端拒绝写 | 回放不能二次改线上数据 | 前端已有写门禁（拒绝 CAVE `/api/` 非 GET）+ `readonly_replay_flag`；服务端侧仍空缺 |
| B-06（BV07） | `replay.asset.resolve`：历史资产解析，读不到时给 `status + reason` | 过期/撤权/丢失过期、撤权、丢失都要有明确降级 | 现在缺失只能标 `unavailable`，容易变成"用最新数据悄悄补上" |
| B-07（RB07 + BV05） | chunk manifest + 多来源 manifest（EM/SV/graph/mesh/分辨率/坐标变换） | V_loaded 的版本化引用；keyframe 前后端交叉校验 | 无 |
| B-08（BV03/BV04） | EM revision 与 mesh build/version/LOD 可查、可重读 | 历史 EM/mesh 失效时必须报错而不是画新的 | 公开栈 EM 版本无关可重取；mesh 时态无 |

### 第三组：局部资产导出（训练材料）

| ID | 内容 | 字段 | 现状 |
|---|---|---|---|
| B-09（B11/B12/B13） | 编辑前后同 ROI 标签体 + 变化体素/差异摘要 | `segmentation_before_uri/after_uri, checksum, dtype, resolution, changed_voxel_count` | 主项目有 CB2 侧 mask 重建能力（NCC 0.84–0.95），但**没有按 edit 自动打包**的异步作业 |
| B-10（B14） | 同 ROI 原始 EM（可选，训练/复核用） | `em_roi_uri, image_source_version` | 无 |
| B-11（B15 + RB06） | 异步 ROI 导出任务（job id / status / manifest），不被体素导出拖慢编辑接口 | `roi_export_job_id, status, output_manifest` | 无；现在只能同步拉，大 ROI 会堵 |

### 第四组：治理（上线前必须，试点可延后）

| ID | 内容 | 不做的后果 |
|---|---|---|
| B-12（B16） | 权限、匿名化、配额、审计、留存策略 | 私有数据或 ROI 批量下载失控 |
| B-13（RB08） | 保存请求/回执与延迟摘要（**不得采 token/敏感 header**） | 画面缺失时无法定位"是请求失败还是本来没加载" |
| B-14（D16） | 断网缓存：本地队列 + ACK 续传，限额，不采非业务键盘 | 断网即丢；重连重复上报 |
| B-15（D20） | 截图/历史 ROI/事件的保留期与可见范围 | 合规风险 |

## 建议顺序（按依赖，不按优先级分值）

```
1  B-01 回执链            ← 没有它，join/样本/验收全都只能"估计"
2  B-04 版本引用 + 只读源  ← R2 的门槛，配合 B-05
3  F-03 V_loaded           ← 与 B-07 一起才有意义；决定 R2 是否可信
4  F-01 / F-02 工具与动作  ← 有了它，PP04/PP05 才能真正落地
5  B-09/B-10/B-11 资产导出 ← 训练材料，可并行
6  B-12~B-15 治理          ← 试点前完成，试点后可继续
7  F-04/F-05/F-06 增强     ← 有余力再做，不影响 R1+R2 主要结论
```

为什么 1、2 排在前面：这两项是**唯一会让已有产物"看起来对但实际不可信"**的地方。
其余项缺了只是少字段，缺这两项会让回放/样本在版本上撒谎。

## 在补齐之前，下游必须怎么读我们的数据

| 场景 | 可以下结论 | 不可以下结论 |
|---|---|---|
| 有 `keyframe.capture` 且 `capture_status=captured` | 这个时刻的画面（EM/分割叠加）就是当时所见 | 当时的 Root 归属也是这个（需 B-04） |
| `cave_join` 命中 `exact-anchor` | 会话与某次 op 时间上对齐 | 这次 op 就是这次提交（需 B-01） |
| `derived/episodes.jsonl` 的 `no_edit=true` | 这段没有提交编辑 | 这段"检查过没问题"（D15/PP10） |
| `idle_segments` 有值 | 这段时间没有输入 | 这段人在思考 |
| `capabilities().v_loaded` 为空 | 我们没采加载态 | 画面当时完整显示 |

## 每项的"改完"怎么证明（沿用需求清单的验收方法）

| 项 | 证据 |
|---|---|
| F-01 | 一份 action→operation 对照表，前端动作与服务端执行一一对应 |
| F-02 | 一次 Split 的草稿 sources/sinks 与预览形状，与服务端最终结果逐点一致 |
| F-03 | 断网/弱网日志：失败 chunk 在事件里出现，恢复后补拉可见 |
| B-01 | 人为制造 502：服务端只执行一次，按 request_id 查到最终状态 |
| B-04 | 让另一个账号同时 Merge/Split，再回放旧时间点，画面与归属仍是旧版本 |
| B-05 | 回放期间抓审计日志：零生产写调用 |
| B-06 | 过期/撤权/丢失各一例，返回 `status+reason`，不返回最新文件 |
| B-09/B-10 | 两份 mask 可直接比较、SHA256 可校验、含 operation_id |
| B-11 | 编辑接口响应时间不受导出耗时影响 |
| B-12~B-15 | 跨用户访问被拒；大任务限速；断网恢复无重复无丢失 |
