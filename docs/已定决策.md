## 0. 主线是“复刻”，分段是后处理（2026-10-26 用户定）

这句话决定了后面很多取舍，放在最前面：

| | **复刻（主线）** | 分段（后处理） |
|---|---|---|
| 目标 | 任意时刻都能把当时画面一模一样重画出来 | 把连续流切成“段”，当统计/训练单位 |
| 要不要阈值 | **一个都不要** | 全靠阈值（静默多久、跳多远） |
| 输入 | 完整 state 序列 + 图 + 版本 | 复刻所需的一切（分段只是附加索引） |
| 错了怎么办 | 不能错（错了就是没还原） | 重算即可，原始数据不动 |

推论：

1. **L1 工作段、三套阈值、PP08/PP09 全部推到后处理**，不进采集主线，也不阻任何采集/回放工作。
2. 复刻真正需要的只有三样：**完整 state（不是摘要）、每个变化点都有、以及能指向当时版本**。
   前两样 **2026-10-26 已落地**（recorder v0.9：每个 `viewer.state-change` 带完整 state，
   约 470 B/次 ≈ 1 MB/小时；回放与保真度都改用这些点）。剩 **版本** 一项卡后端。
3. 所以下面第 1、4 节保留作讨论记录，但当前不实现。

## 1. 任务边界：不让人声明开始/结束，事后切分（后处理，暂缓）

### 1.1 约定

标注员**直接做自己的标注工作，不点"开始/结束"**；我们在后处理阶段把连续操作切成"工作段"。
依据：`Q02` 已确认"自由浏览、无预设任务队列、不得预设任务边界"；`PP07` 原文即"自由浏览无自然 task_id"。

### 1.2 代价与收益（用户要求保留，作为后续讨论依据）

| 放弃的 | 换来的 |
|---|---|
| 无法区分"看完这个神经元算结束"和"中途接了个电话回来接着看" | 人完全不被打断，操作是真实工作流 |
| 没有"任务级 no-op"（这一段到底有没有被完整检查过） | 不需要任务系统、不需要培训标注员"记得点开始" |
| 边界准确率只能靠抽样人工校（要花一点专家时间） | 数据可以用现成的历史/公开操作跑，不用等流程改造 |

### 1.3 切到什么程度（4 级，全部机械可解释）

| 级别 | 定义 | 粒度 | 用途 |
|---|---|---|---|
| L0 会话 | 一次上机 | 分钟~小时 | 归档 |
| **L1 工作段** | 静默 < 阈值 + 同一 root 族 + 工具上下文不变 | 1–20 分钟 | **后处理阶段再加（暂缓）** |
| L2 观察片段 | 空间跳变 / 短静默切出 | 3–60 秒 | 决策样本容器、回放跳转锚点 |
| L3 编辑尝试 | 以 `edit.request` 为锚 ± 窗口（含 preview/ack/undo） | 10–120 秒 | 提交链路对齐、训练正例 |

### 1.4 永远无法从行为里得到的东西

- **意图**：他为什么看这里（只能靠书签/问卷，且覆盖率低）。
- **"看完"与"离开"**：两者在数据上都是"长时间无输入"。
- **任务级 no-op**：没有边界就没有"这一段被完整检查过"这个命题。
这三条不要指望通过改算法解决；只能靠"人偶尔说一句"（`evidence.bookmark` / prompt）来补。

### 1.5 将来用什么测量来定阈值

`PP07` 原定验收是 `Boundary IoU / F1`，靠人工勾边界。**2026-10-26 用户决定不投人工**，改用两个机器可做的比较（详见第 3 节）：

| 替代办法 | 能回答 | 不能回答 |
|---|---|---|
| 脚本已知真值（模拟时我们自己知道在哪进下一段） | “算法能不能把我故意插入的切点找回来” | 真人心里怎么算一段 |
| 回放保真度（恢复 state 后重渲染 vs 当时那张图） | “记录是否忠实、能不能重放出当时画面” | 分段是否符合真人习惯 |

两个都是**上界型**证据：脚本切点是机械的、精确的，所以它证明的是“管道通、不漏切”，
不是“切分准确率 0.83”。想拿到后者必须有人勾线，这是不投人工就**得不到**的唯一一项。
在此之前，同时产出三套阈值版本（见第 4 节），不预设哪套是对的。

### 1.6 现在默认怎么跑

按"自动推断"跑：只产 L2（已有）+ L1（待实现），每条标 `boundary_source='auto.rule'`，**任何文档/字段都不写"任务"**。

## 2. 日志粒度：move 采多细（**已做成可配**，2026-10-26）

### 2.1 这是个功能，不是常量

| 设法 | 用法 |
|---|---|
| `R.setConfig({move_sample_ms: 0})` | 控制台/工作台，运行中改也生效 |
| URL 加 `?cave_move_ms=0` | 不想开控制台时 |
| 什么都不做 | recorder 默认 50；采集面板默认 0 |

生效值写进 **三处**：`session.start.config`、会话包 `manifest.config`、派生 `normalized.json.sampling`。
运行中改会补一条 `collector.status{config_change:true}` 事件——**不假装整段同粒度**，下游看到多个 config 必须分段读。

### 2.2 代价对照（实测口径）

| 粒度 | 事件量 | 一小时会话 | 适合 |
|---|---|---|---|
| 50ms | ≈2.7 事件/秒（脚本演示）；真人拖拽时会更高 | 万级事件，包几 MB | 默认；够做手势与轨迹 |
| 0（全量） | 真人拖拽约 60 条/秒 | 十万级事件 | 要精确复现"手怎么移的"/做运动学分析 |

`MAX_EVENTS` 已从 5 万提到 20 万（全量下约撑 55 分钟），超了会记 `dropped` 计数，不静默丢。

### 2.3 相关修正（重要）

2026-10-26 发现：`pointermove` 监听**从来没挂上**，所以"50ms 采样"这段代码此前从未执行，
`input.pointer` 只有 down/up/click 端点，手势的 `n_raw`/`path_px` 也一直偏小。
现已挂上（并补 `pointercancel` 收尾）。验收方式：同一毫秒连发 200 个 move，50ms 采样只应落 1 条、全量应落 200 条。

## 3. 人工抽检：已决定不投（2026-10-26），改用机器对比

### 3.1 先分清两件很像但不同的事

| | 内容对不对 | 切分准不准 |
|---|---|---|
| 是什么 | 这段看到的是不是同一个神经元、merge 对不对 | 自动切的线是否对得上人实际的工作单元 |
| 影响谁 | **训练标签** | **只是派生层索引**（原始事件一点不变） |
| 需不需要人 | 将来可能要（专家复核，`PP11/PP12`） | 原本要，**现在决定不要** |

用户判断（2026-10-26）：**我们只要如实记录，不需要人去判数据对不对**。这条对：
原始事件是采集器如实写的，不靠人确认；切分只是`derived/` 里的索引，错就重算。

### 3.2 不投人工的代价（写清楚，不掩饰）

- 得不到“切分准确率 = 0.83”这种面向真人边界的数字；
- 三套阈值里选哪套，只能靠“机械切点能不能找回” + 人工读几个例子，不能靠统计选择；
- 将来若要报这个数，必须补一次勾线（成本仍是 15–60 分钟）。

### 3.3 改用的两个机器验法（已实现）

| 办法 | 怎么做 | 实测 |
|---|---|---|
| **脚本已知真值** | 模拟脚本在进入下一段时打一个 `mark`（浏览器墙钟）；派生后用 ±10s 容差看切点能否找回 | demo：**2/2 找回**，额外 1 个切点（回看原处，真跳变） |
| **回放保真度** | 逐个 checkpoint 发 `state`，等 position 到位、瓦片画完，读 canvas 像素，与当时那张关键帧比（缩到 256×256 算 NCC） | demo：**5/5 对比，平均 NCC 0.994，最低 0.9848**（其中一张 1.0 像素级一致） |

回放保真度是**“我们只是想要如实记录”这句话的直接证据**，而且它能同时充当
V_loaded（没加载完会低分）与版本锁（版本不同会低分）的验收装置。
**已接进 demo 当作 PASS 条件**（`demo_capture_episodes.py` 默认跑，`--no-fidelity` 可跳过）：
平均 NCC < 0.90 或最低 < 0.80 就直接 FAIL，不用人看。
单独跑：`python3 scripts/verify_replay_fidelity.py <会话包目录>`

### 3.4 前提条件

回放保真度要求“每个 checkpoint 都有一张图”，所以需打开
`keyframe_on_checkpoint`（默认关，每 30s 一张图≈120 MB/小时）：
`?cave_kf=1` 或 `R.setConfig({keyframe_on_checkpoint:true})`。
没开的会话包，脚本会直接报 `skip` 并告诉你为什么，不会假装算过。

## 4. 切分策略多版本并存：是什么、为什么（**暂缓**）

> L1 与三版本阈值都属后处理层；主线复刻不需要它们。此节保留作以后讨论。

### 4.1 是什么

同一批原始事件，用 3 组阈值各切一次，产出 3 份派生结果（各几 KB），每份带自己的 `policy_id`：

| 版本 | 静默阈值 | 空间阈值 | 用途 |
|---|---|---|---|
| `seg.loose` | 300s | 400µm | 只切明显断开，边界少、误切少 |
| `seg.normal` | 120s | 200µm | 默认 |
| `seg.tight` | 45s | 100µm | 切得碎，当"候选边界"给人工勾 |

原始事件**不动**；派生随时可重算。

### 4.2 好处

1. **阈值不该由我拍**——它是个可以用数据选出来的参数；并存三份就有机会选。
2. 不同下游要不同粒度：训练 Agent 要小片段（L2），人工复核/汇报要大段（L1）。
3. 出错可回退：发现 `normal` 切坏了，`loose` 可能还在。

### 4.3 坏处与规避

- 风险：下游混用两版做统计 → 结论自相矛盾。
- 规避：每条记录带 `policy_id`；导出/训练/评估入口**锁定一版**并写进 manifest。

## 5. PP08 / PP09：定义、好处、坏处（清单原文 + 现实含义）

两条都是 `P1`、都在离线、都明确"只出候选不当真值"，**都不阻塞采集与回放**。

### 5.1 PP08 弱监督动作标签

清单原文：`定位/检查/比较/草稿/验证/放弃等候选 | 可训练的语义化轨迹 | macro-F1 | P1 | 输出概率和版本`

现实含义：把"鼠标动了 37 下"变成"先定位 → 看 EM 检查 → 对比两段 → 试了草稿 → 放弃"。

| 做法 | 好处 | 坏处 |
|---|---|---|
| A 只做机械动作段（move/zoom/select/键） | 零猜测、可复算、现在就能做 | 不叫语义，训练价值有限 |
| B 机械 + 可计算派生（+revisit / dwell / draft-abandon） | 仍零猜测，但能表达"回看""犹豫" | "犹豫"仍是推断，必须标来源 |
| C 规则映射成语义标签 | 拿到语义轨迹 | 规则是人写的，错在规则上；不同人写的不一致 |
| D 模型预测 + 置信度 | 可扩展 | 要先有 B 的原料 + 人工抽检校准；没校准就是自证 |

**当前默认**：停在 B。理由：B 的每个标签都能从原始事件重算，且不含"我认为他在比较"这种判断。

**底线**：不能用"后来提交成功"反推"当时他在验证"——那是把答案写进输入。

### 5.2 PP09 重点观察候选排序

清单原文：`强锚点+回看+多视角+预览结果+用户书签 | 帮助专家找关键证据，不当真值 | Recall@K | P1 | 编辑点≠证据点`

现实含义：给专家/Agent 一个"先看这里"的顺序，**不是**真值标签。

| 信号 | 单独用的陷阱 |
|---|---|
| 强锚点（提交/撤销位置） | 提交点是"结果位置"，不是"证据位置"（清单明写） |
| 回看（同区域 ≥2 次进入） | 反复看也可能是没看懂 |
| 多视角（换朝向/尺度） | 也可能只是随手拖 |
| 预览结果 | 只有 fork 之后才有 |
| 用户书签 | 覆盖率低 |

**当前默认**：输出 5 个分项，**不排序、不给单一 score**。理由：这些信号可靠性差一个量级，压成一个数会把噪声放大且无法解释。

## 7. 已拍板：不再往“渲染过程”方向扩（2026-10-26）

**决定**：行为采集与回放的范围冻结在已有字段（`input.pointer` / `input.wheel` /
`input.key` / `viewport.gesture` / `viewer.state-change` / `viewer.checkpoint` /
`keyframe.capture` / `selection.change` / `evidence.bookmark` / `edit.*`），
**不新增** tile/shard manifest、mip 剖面、chunk 级“画了哪些块”。

**理由**（实测，不是判断）：

- 页面内 `performance` 只看得到 **14** 条（全是 `/info`、`/state`），
  tile 请求在 **Worker** 里，注入式采集器拿不到；
- 浏览器网络层（Playwright/CDP）能看到 **112** 条，但 URL 只到 **shard + mip**
  （`/em/8_8_40/03b98.shard`），到不了单块；且“请求过”≠“画进这一帧”；
- `viewer.chunkManager` 存在，但没有 `visibleChunks`，真状态在 Worker（RPC 代理）——
  要拿就得包 `Worker`，风险与 fork 相当。

**代价与可接受性**：失去“为何这两帧差 1%”的归因能力；保留
`content{colored,thumb16_sha}` + `self_ncc` 作为“拍早了”的判据——已足够驱动
`painted_partial` / `motion_lag` 两类标记。将来若反复出现“state 对、图就是差一截”
且说不清，再重新评估 L2（需改 NG 源码）。

## 8. 已拍板：像素 0.95 不是主线门，界面级回放是主线（2026-10-27 用户定）

**背景**：`replay_manual_session.py` 的像素门（段末 rgb NCC ≥ 0.95）在真实长会话上
反复不过（0.72–0.92 波动）。查下来位置 Δ=0、选中集/布局一致、2D 涂色一致，
差异只在 **EM 瓦片加载深度（LOD）**：回放端取到的细节层和录制端不同，
而 NG 没有"瓦片加载完成"的信号（见 开发记录 同日条目）。

**用户判断**：操作和所见已经复刻，画面糊一点可以接受；像素清晰度不算主线工作。

**现在的默认（承诺）**：

| 项 | 状态 |
|---|---|
| 主线验收 | 位置 Δ ≤ 60 nm、选中集/层/布局一致、能界面级拖动回看 |
| 像素 NCC | **参考指标**：照常算、照常打印，>0.90 记“接近”，<0.90 记“明显差异”，**不阻断** |
| `--accept-ncc` | 保留，默认 0.95；要"人眼验收"口径时显式传 `--accept-ncc 0.90` |
| 3D 面板 | 默认从像素比对中排除（`4panel` 左下），`--compare-all` 可回整图 |

**为什么不做**：继续追 0.95 需要改 NG 源码拿瓦片可见集（见本文第 7 节评估：L2 代价与
fork 相当），收益只是"数字好看"，对"能不能复刻操作与所见"没有增量。

**将来用什么测量量重新评估**：如果出现“state 一致、位置一致，但有人肉眼能看出画面
内容不同（不是清晰度）”，再把像素门提回主线——那时差异是**内容**而不是**清晰度**。

**已实现的界面级回放入口**：`scripts/cave_replay_studio.py`（真 NG + 可拖时间轴 +
右侧数据面板；拖动 = 跳 state 快照，逐条输入重放仍走 `replay_manual_session.py`）。

## 9. 已拍板：不做 1 Hz 心跳（2026-10-26）

心跳由采集器自己发，**无法区分“人走了”与“采集器死了”**；实测还占事件流 28%。
替代：输入事件的静默区间（离线可算）+ `seq` 连续性 + `gaps[]`（带 `t_end`）+
宿主侧轮询 `R.status()`。若将来需要“每秒一条”的可视化时间轴，在派生层按秒聚合，
不写回原始事件。
